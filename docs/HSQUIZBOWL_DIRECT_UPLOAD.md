# HSQuizbowl Resource Center direct upload — research and gate (#767)

Status: **direct upload is not supported**. This is the legitimate outcome B of
issue #767: no supported third-party stats-publishing API was found, so QBSheet
stops at safe file preparation plus browser handoff (issue #766) and must not
ship undocumented form automation.

- Research last verified: **2026-09-10**
- Verifier: `fix/767-hsqb-upload-gate` (PR closes #767)
- Code gate: `src/director/publish/hsqbUploadGate.ts`
- Gate tests: `src/director/publish/hsqbUploadGate.test.ts`

## What was checked

1. **ACF statkeeping guide** (`https://acf-quizbowl.com/guidelines/stats/`,
   fetched 2026-09-10, HTTP 200). The "Managing Stats" section documents only
   an authenticated browser workflow, and nothing else:
   - sign into the forum account that owns the tournament entry;
   - select the tournament;
   - `Edit tournament listing` → `Manage stat reports` → `Add stat report`;
   - upload the HTML files generated by YellowFruit or SQBS.
   - Only the owner of a database entry may post statistics for it.
   - Multi-phase tournaments post each phase separately plus a combined file.
   - No API, API token, OAuth flow, or third-party write integration is
     mentioned anywhere on the page.

2. **Live Resource Center** (`https://hsquizbowl.org/db/`, fetched 2026-09-10).
   Returns HTTP 403 to an unauthenticated fetch, consistent with a
   phpBB-gated application rather than a public API surface. There is no
   public developer/API documentation to evaluate there.

3. **Architecture history** (`https://hsquizbowl.org/forums/viewtopic.php?t=15787`,
   referenced in #760/#767 research). The Resource Center maintainer has
   described the database as a PHP/MySQL application tightly integrated with
   phpBB for login/authentication. The thread itself is bot-gated (HTTP 403 on
   2026-09-10) so it was not re-fetched here; future re-checks should confirm
   whether that coupling still holds.

4. **YellowFruit reference** (`https://github.com/ANadig/YellowFruit`, GitHub code
   search 2026-09-10 for `hsquizbowl`). Two matches: `README.md` and
   `src/renderer/Components/AboutYfDialog.tsx` — documentation/about text only.
   No upload client, API token handling, or `hsquizbowl` network integration
   was found, corroborating that the established ecosystem still treats
   Resource Center publishing as a separate authenticated browser step.

5. **QBSheet itself** (2026-09-10). Code search for `hsquizbowl` across `src`,
   `packages`, and `docs` finds no upload client, no stored forum credentials,
   no cookie handling, and no CSRF-token replay. The gate below keeps it that
   way by failing closed.

## Decision

Direct publication of stat reports to the Quizbowl Resource Center is
**unsupported until the Resource Center documents or explicitly approves a
stable third-party authentication/upload contract**. The supported workflow is:

1. Prepare the report files offline in Director (issues #762–#764).
2. Follow the `Prepare for HSQuizbowl` handoff (issue #766): extract the files
   and choose each one in the Resource Center's `Add stat report` form.
3. The one verified field mapping is Resource Center `Scoreboard` →
   the report file ending in `_games.html`.

## Prohibited mechanisms

QBSheet must never implement direct upload by any of the following, even if
they appear to work:

- asking for the user's forum password inside QBSheet;
- storing a phpBB password in Director state, localStorage, or any export;
- scraping cookies from an existing browser session;
- copying session cookies between apps;
- programmatically replaying CSRF tokens from undocumented forms;
- embedding a hidden browser that logs into the forum and submits forms.

Secrets or tokens from a future approved mechanism must use OS-appropriate
secure credential storage on native Director, must never be exported in
`.qbst`, QBJ, backups, diagnostics, or logs, and must follow the provider's
documented security model in the browser.

## What a future supported integration must document first

Before any upload code lands, all ten questions from #767 Phase 1 must be
answered in this file: existing write API, maintainer willingness,
authentication mechanism, ownership/authorization model, supported operations
(list/create/replace/delete), required vs optional report fields, upload
encoding (multipart HTML, archive, structured stats/QBJ), size/content limits
and validation errors, staging/test environment, and rate limits/versioning.

Implementation requirements when that day comes (from #767 Phases 2–4):

- Network integration behind the narrow `ResourceCenterPublisher` interface in
  the gate module, separate from report generation.
- Uploads consume the same preflighted report artifact as manual export.
- Ownership comes from server-returned writable tournaments (stable IDs),
  never from matching tournament names.
- Explicit publish action showing target tournament, report name/scope, and
  create-vs-replace semantics; no silent republish on local changes.
- Explicit handling for expired/revoked auth, non-ownership, not-found,
  duplicates, parser rejections, partial failure, rate limiting,
  network loss, and unknown schema versions.
- A failed upload leaves the local generated report intact for manual upload.
- `Published` is shown only on a verified provider response carrying
  per-file/parser success (never on a bare 2xx, never on local generation).
- Mock contract tests, sanitized fixtures, no real secrets in CI, network
  tests opt-in and separate from offline CI, manual fallback stays tested.

## Re-check procedure

1. Re-fetch the ACF guide and look for any API/token/OAuth mention.
2. Check `https://hsquizbowl.org/db/` and the forums for developer
   documentation or a maintainer announcement of third-party integration.
3. Re-run the YellowFruit code search; a new upload client there is a strong
   signal the contract exists.
4. If anything changed, update the verification date above and answer the
   Phase 1 questions before writing upload code. If nothing changed, update
   only the date.
